## Feito — relatório item por item

Portão: `scripts/medir-portao-sis274.mjs` → `docs/medidas/portao-sis274.json`
Asset: `scripts/gerar-logo-portao-sis274.mjs` → `docs/medidas/logo-portao-sis274.json`

### Antes de tudo: a premissa do «fundo preto» não se confirmou (de novo)

A issue prescreve «usar mask/`mix-blend`/asset com alfa, ou recorte do símbolo branco». Nenhum dos três foi usado, porque o problema não existe — e é a mesma constatação que a SIS-265 já havia registrado. Medido em `public/logosistranaltadefinicao.png`:

| | |
|---|---|
| `hasAlpha` | `true` |
| pixels em `alpha = 0` | **80,6 %** |
| cantos e centro | `[0, 0, 0, 0]` |
| pixels **opacos escuros** | **0** |
| luminância média dos opacos | **254,8 / 255** (símbolo branco) |

O `0,0,0` que aparece em visualizador que ignora alfa está guardado **sob** os pixels transparentes. `mask`, `mix-blend-mode` ou `threshold` ali estragariam a antisserrilha do anel (300.582 pixels de alfa parcial) para resolver um problema inexistente. Aplicado: só reamostragem premultiplicada + WebP.

### 1. «Em qualquer navegação de rota, overlay = `#1273bc` (não o navy atual)» ✅

Medido nos **dois** caminhos, porque o portão é remontado por `key={usePathname()}`:

| caminho | `backgroundColor` | `backgroundImage` |
|---|---|---|
| primeiro carregamento (`/`) | `rgb(18, 115, 188)` | `none` |
| troca por **clique** → `/trabalhe-conosco` (`urlDepois: "/trabalhe-conosco"`) | `rgb(18, 115, 188)` | `none` |

`backgroundImage: none` importa: saiu o degradê navy **e** o `radial-gradient` de ciano a 14 %. O brilho tinha de sair junto — ele existia para levantar um navy quase preto; sobre `#1273bc` ele só lavaria o centro, exatamente onde a logo branca precisa de contraste.

A medida da troca de rota exigiu `MutationObserver` instalado **antes** do clique: a primeira versão do portão usava `waitForSelector` e devolveu `null`, porque o overlay pode nascer e morrer entre duas idas ao navegador — e espera que falha em silêncio é indistinguível de «não apareceu».

### 2. «Centro = logo HD, sem texto “SISTRAN”» ✅

- `textoVisivelDoOverlay: "Carregando…"` — o texto **inteiro** do overlay. A palavra «SISTRAN» não está lá. Medido pelo texto, não pelo seletor `.wordmark`: apagar a classe e deixar a palavra passaria num portão que olhasse só o seletor.
- `<img src="/images/loading/logo-sistran-portao.webp">`, `naturalWidth: 320` — carregou de verdade. Um 404 daria tela azul vazia, que também «não tem texto SISTRAN»; há listener de `response` no portão e `erros: []`.
- A regra `.wordmark` saiu inteira do CSS, não só a cor: sem consumidor no JSX ela seria CSS morto.

Observação de fato: o PNG HD é **só o símbolo** (anel + swoosh), sem letreiro. Então a troca remove as letras por construção — é o que o critério pede.

### 3. «Sem caixa preta» ✅

Provado em **dois** níveis, arquivo e pixel renderizado.

No arquivo derivado, achatado sobre `#1273bc`: `cantosTodosIguaisAoFundo: true`, **`perimetroForaDoFundo: 0`** (perímetro inteiro, não só os quatro cantos — moldura arredondada passaria por cantos).

Na tela, moldura de 12 px ao redor da caixa de 128×128 da logo:

| | |
|---|---|
| `pixelMaisEscuroDaMoldura` | **`[18, 115, 188]`** — o próprio azul |
| `pixelsForaDoAzul` (tol. ±6/canal) | 144 |
| `piorDesvioPorCanal` | 16 (todos **clareando**) |

O número que fecha o critério é o primeiro: o pixel mais escuro de toda a moldura **é o fundo**. Não existe nada mais escuro que o azul ao redor da logo. Os 144 são contáveis de antemão e são a grade de 48 px: moldura de 152 px ⇒ 3 linhas verticais + 3 horizontais, cada uma cruzando a faixa de 12 px em dois lados ⇒ 6 × 12 × 2 = 144.

### 4. «Nitidez OK» ✅

| DPR | arquivo | CSS | pixels de dispositivo | arquivo ÷ dispositivo |
|---|---|---|---|---|
| 1 | 320 | 128 px | 128 | **2,50** |
| 2 | 320 | 128 px | 256 | **1,25** |

Acima de 1 nos dois casos — nunca há ampliação de bitmap. `clamp(4.5rem, 16vw, 8rem)` em `width`: o teto de 8 rem = 128 px foi o que decidiu o lado 320 do asset (128 × DPR 2 = 256, com folga).

Peso: **324.169 → 11.154 bytes (−96,6 %)**. A derivada é obrigatória e não opcional: com `images: { unoptimized: true }` (SIS-154) o `next/image` serviria o mesmo arquivo sem `srcset`, então 324 KB de arte 1254×1254 entrariam no caminho crítico do overlay que cobre **toda** troca de rota e vem no HTML do servidor — a tela ficaria azul e vazia até a logo chegar. É `<img>` cru com `eslint-disable` documentado, como nas outras nove ocorrências do projeto (padrão do `OptionalMorphIntro`), mais `width`/`height` intrínsecos para a caixa não pular.

### 5. «Manter barra/sinal animado se continuar legível no azul novo; senão ajustar contraste» — ajustado ✅

Não continuava legível. Contraste sobre `#1273bc` (WCAG 1.4.11 pede 3:1 para gráfico):

| tinta | contraste | |
|---|---|---|
| `#2ac4ff` (o sinal atual) | **2,48:1** | reprova |
| `#0ed8f6` (o ciano mais claro da paleta) | **2,90:1** | reprova |
| `#fff` | **5,00:1** | passa |

Nenhum ciano da marca alcança 3:1 contra este azul — os dois estão na mesma faixa de luminância. O sinal **foi mantido** e virou branco: `corDaBarra: rgb(255, 255, 255)`, trilha em `rgb(255 255 255 / 0.28)` (senão o sulco sumiria e a barra pareceria correr no vazio) e o halo do `box-shadow` também em branco (halo ciano sob barra branca daria franja esverdeada).

A grade de 48 px do `::before` seguiu a mesma regra e passou de ciano 6 % para branco 8 %: sobre `#1273bc` o ciano a 6 % cai no tom do fundo e a grade desapareceria — sobraria uma regra morta. Os 5,00:1 do branco são o mesmo número já medido e comentado no `Social.tsx` para este azul.

### 6. «Acessível: `alt=""` decorativo + status “Carregando…” (`sr-only`) permanece» ✅

`altVazio: true` (atributo presente e vazio — ausente seria outra coisa para leitor de tela), `status: { texto: "Carregando…", ariaLive: "polite" }`, `marcaAriaHidden: true`. Também `backgroundColor: rgba(0,0,0,0)` e `mixBlendMode: normal` no próprio `<img>` — nada de caixa vinda do CSS do nó.

### 7. «Reduce motion: sem regressão» ✅

Os **dois** canais da casa, medidos separadamente:

| | media query `reduce` | `html[data-motion="reduce"]` |
|---|---|---|
| `animationName` do sinal | `none` | `none` |
| largura da barra | **240 px** (trilha cheia) | **240 px** |
| `transitionDuration` do overlay | `1e-05s` | `1e-05s` |
| logo | 128 px, visível | 128 px, visível |

A decoração morre **visível** — a barra fica preenchida de ponta a ponta em vez de congelar em 42 %. O `1e-05s` é o reset global de reduced-motion do `globals.css` (0,01 ms), não uma transição sobrevivente. Capturas conferidas: `sis274-portao-1440-carregamento.png`, `-troca-de-rota.png`, `-reduce.png`.

`npm run lint` → **79 problemas (31 erros, 48 avisos)** — exatamente a linha de base documentada, e **zero** problemas nos arquivos tocados. O `@next/next/no-img-element` que o `<img>` novo levantaria está silenciado com o motivo na linha, como nas nove ocorrências já existentes.
