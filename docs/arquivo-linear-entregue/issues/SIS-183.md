O mesmo padrão já reapareceu em `events-spotlight.css` e `legacy.css`. **Ninguém garantiu que não há um terceiro caso.**

## O mecanismo (já documentado na casa)

Este site tem **dois** jeitos de reduzir movimento:

1. `prefers-reduced-motion: reduce` do sistema
2. o botão da interface, que grava `html[data-motion="reduce"]`

O botão funciona em JavaScript porque `layout.tsx` embrulha `window.matchMedia` — todo hook vê o valor escolhido. Uma `@media (prefers-reduced-motion: …)` de verdade **não é interceptável**. Então toda regra CSS que decide layout/posição/display por essa at-rule precisa de um **espelho** `html[data-motion="reduce"] …` (e, quando a regra positiva é `no-preference`, a guarda `html:not([data-motion='reduce'])` no seletor que liga o modo dirigido).

O padrão bom está escrito em:

* `src/components/ui/metrics-band-track.css:183-260` (nota longa + espelho + `html:not([data-motion='reduce'])`)
* `partners-track.css` (\~248)
* `events-spotlight.css`
* `legacy.css`

## O que fazer

### 1. Inventário

Listar **todas** as ocorrências de `@media (prefers-reduced-motion` em `src/**/*.css` e nos CSS modules. Para cada uma, classificar:

### 2. Conferência com o botão, não só com a preferência do SO

## Pontos de atenção

* Não “corrigir” com JavaScript o que é regra CSS — o embrulho de `matchMedia` já cuida dos hooks; o buraco é at-rule.
* Não alargar o reset global `html[data-motion="reduce"] * { animation: none }` para cobrir layout. Layout precisa de seletor explícito; o reset global não devolve `position: static` nem apaga espaçador.
* Código/comentário que documenta o espelho é especificação: nota nova no mesmo formato das existentes.
* Escopo é **auditoria + reparo dos buracos**. Não refatorar motion policy, não tocar no script de `layout.tsx`.
